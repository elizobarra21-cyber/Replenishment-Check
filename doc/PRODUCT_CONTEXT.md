# Product Context

## Что мы делаем

Мы делаем Telegram miniapp для пополнения магазина. Сотрудник в торговом зале фотографирует этикетку товара, отмечает размеры, которые уже есть в зале, а приложение формирует список того, что нужно забрать со склада.

Проект называется `store-replenishment`.

В продукте нет и не планируется каталога товаров или базы того, что лежит на складе. Это умный список, который заменяет ручную запись: все рабочие данные берутся из скана этикетки и выбора размеров сотрудником.

## Пользовательский сценарий

1. Сотрудник в зале открывает miniapp на телефоне.
2. Делает фото этикетки товара.
3. OCR на клиенте локализует штрих-код и читает 17-значный код только из узкой полосы непосредственно над ним (распознавание только цифр; сам баркод и другие числа на этикетке не читаются).
4. Приложение извлекает из кода:
   - `article` - первые 7 цифр;
   - `color` - следующие 3 цифры;
   - следующие 2 цифры игнорируются;
   - `season` - следующая 1 цифра;
   - `storage` - последние 4 цифры.
5. Сотрудник может поправить распознанные поля вручную и при желании выбрать визуальный цвет товара из палитры (ходовые цвета в один тап или произвольный из спектра).
6. До, во время или после сканирования сотрудник выбирает размеры, которые уже есть в зале: `XS`, `S`, `M`, `L`, `XL`.
7. Один размер можно выбрать несколько раз.
8. Выбранные размеры показываются под плитками; нажатие на выбранный размер удаляет одну штуку.
9. `Suggested sizes` показывает размеры, которые нужно добавить, исходя из правила: в зале должен быть набор `XS S M L XL`.
10. После `Add to list` товар попадает в краткий складской список.
11. В `Warehouse mode` склад видит товары по `storage` из этикетки, в порядке обхода склада, с нужными размерами и справочной информацией.
12. Список заявки сохраняется между перезагрузками страницы и потерей связи (по `requestId` в `localStorage` с восстановлением из БД). Текущий режим (`hall`/`warehouse`) тоже сохраняется и восстанавливается. Очистить список можно только кнопкой `Finish replenishment` (есть и в зале, и на складе), которая завершает заявку и заводит новую.

## Текущее продуктовое правило по размерам

Для зала обязательный набор:

```text
XS S M L XL
```

`Suggested sizes` - это отсутствующие размеры из этого набора.

Примеры:

```text
present: -
suggested: XS S M L XL

present: XS
suggested: S M L XL

present: XS M M
suggested: S L XL
```

Количество больше одного в `present` не меняет целевой набор: если размер уже есть хотя бы один раз, он не предлагается.

## Код этикетки

Целевой код - 17 цифр над баркодом. OCR может вернуть код слитно или с пробелами.

Пример:

```text
48291011234567890
4829101 123 45 6 7890
```

Разбор:

```text
4829101 123 45 6 7890
article color skip season storage
```

Старый короткий формат вроде `48291 123 2 0101` не является целевым форматом.

## Основные экраны

### Hall mode

Порядок блоков:

1. `Label scanner`
2. `Last parsed code`
3. `Choose existing sizes`
4. `Suggested sizes`
5. `Add to list`
6. `Go to warehouse`
7. `Finish replenishment`
8. `Warehouse short list`

Важно:

- Не возвращать OCR preview.
- Не возвращать scanned article dropdown.
- Размеры `XS S M L XL` должны быть доступны до завершения OCR.
- Поля `Last parsed code` должны быть редактируемыми.
- В блоке `Last parsed code` палитра визуального цвета расположена вплотную к полю `color` (ходовые цвета кружками + выбор из спектра, без текстовых подписей). Выбранный цвет сохраняется в `RequestItem.colorName` и показывается образцом в списке выбранных товаров и в Warehouse mode наравне с кодом цвета.
- После распознавания или ручного ввода `article` товар должен добавляться в складской список без сверки с каким-либо каталогом.

Внутри Prisma может создаваться техническая запись `Scanned article {article}`, но это не каталог товара. Группировка и порядок склада берутся из `storageSection` каждого добавленного элемента.

### Warehouse mode

Warehouse mode показывает компактный список: на товар 1-2 строки внутри группы-департамента.

- группировка по `storageSection` из скана; заголовок группы - `Department {storageSection}`;
- сортировка внутри группы по `article`, затем `season`, затем `color`;
- строка 1: `article` (клик открывает фото скана, если сохранено) и `needed sizes` плитками (акцентные, без `xN`);
- строка 2 (приглушенная): `color` с образцом выбранного цвета, `season`, справочно `present sizes` плитками (контурные);
- у товара есть отметки `Taken` (взяли) и `Absent` (нет в наличии); статус сохраняется в `pickStatus`, отмеченный товар приглушается и зачёркивается, повторный тап снимает отметку;
- `storageSection` показан в заголовке группы и не дублируется в строке товара;
- техническое имя `Scanned article {article}` не показывается, так как совпадает с `article`;
- понятная обработка отсутствия фото.

## Текущий технический стек

- Next.js 16 App Router
- React 19
- Prisma 6
- PostgreSQL (Supabase) для деплоя на Vercel; локально - тот же Postgres через connection pooler
- Tesseract.js на клиенте (постоянный переиспользуемый worker, распознавание только цифр)
- Tailwind CSS 4

## Главные файлы

- `app/page.tsx` - основной экран и клиентская логика.
- `lib/ocr.ts` - клиентский OCR: переиспользуемый Tesseract worker, препроцессинг фото, локализация штрих-кода и выбор строки над ним.
- `lib/colors.ts` - список ходовых цветов и `resolveColor` для палитры визуального цвета.
- `app/api/label/extract/route.ts` - API для извлечения кода из OCR-текста (оставлен для совместимости; Hall парсит код локально через `lib/label-extractor`).
- `lib/label-extractor.ts` - парсер этикетки.
- `app/api/scan/route.ts` - создание элемента заявки и расчет suggested sizes.
- `app/api/requests/[id]/route.ts` - заявка с товарами для восстановления списка (`GET`) и смена статуса (`PATCH`, в т.ч. `DONE` при Finish).
- `app/api/items/[id]/route.ts` - смена `pickStatus` товара на складе (`PATCH`: `taken`/`absent`/`null`).
- `app/api/requests/[id]/warehouse/route.ts` - складское представление.
- `lib/replenishment.ts` - правила расчета размеров.
- `prisma/schema.prisma` - модель данных.
- `lib/prisma.ts` - Prisma Client singleton.
