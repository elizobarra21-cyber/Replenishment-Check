# Development Plan

Документ фиксирует фазы разработки и критерии успеха. Его нужно обновлять, если продуктовый план меняется.

## Фаза 0 - База проекта

Статус: выполнено.

Цель: поднять Next.js + Prisma + SQLite проект с seed-данными и базовыми API.

Критерии успеха:

- `npm run build` проходит без ошибок.
- Prisma schema содержит заявки, элементы заявки и технические сущности для сохранения сканированных артикулов.
- Есть seed-данные для локальной проверки без товарного каталога.
- API умеет создавать заявку.

Ключевые файлы:

- `prisma/schema.prisma`
- `prisma/seed.ts`
- `app/api/requests/route.ts`

## Фаза 1 - Hall scan MVP

Статус: в работе, основа реализована.

Цель: сотрудник в зале может сканировать этикетку, редактировать распознанные поля, выбирать размеры в зале и добавлять товар в список.

Критерии успеха:

- `Label scanner` запускает OCR через `tesseract.js`.
- Парсер принимает 17-значный код слитно и по пробелам.
- `Last parsed code` отображает код с пробелами.
- Поля `article`, `color`, `season`, `storage` редактируемые.
- Плитки `XS S M L XL` доступны до завершения OCR.
- Один размер можно выбрать несколько раз.
- Выбранные размеры отображаются под плитками.
- Нажатие на выбранный размер удаляет одну штуку.
- `Suggested sizes` показывает отсутствующие размеры из `XS S M L XL`.
- `Add to list` сохраняет элемент заявки после распознавания или ручного ввода `article`.
- `/api/scan` не сверяется с каталогом товаров: элемент создается из данных скана и выбранных размеров.
- Вплотную к полю `color` доступна палитра визуального цвета (ходовые цвета кружками + спектр); выбранный цвет сохраняется (`RequestItem.colorName`) и виден образцом в списке добавленных товаров и в Warehouse mode.
- Список заявки сохраняется в `localStorage` (`requestId`) и восстанавливается из БД при перезагрузке/потере связи; очищается только кнопкой `Finish replenishment` (есть в зале и на складе; заявка помечается `DONE`, заводится новая).
- Текущий режим (`hall`/`warehouse`) сохраняется и восстанавливается при перезагрузке.

Оставшиеся риски:

- OCR теперь локализует штрих-код и читает только зону над ним с whitelist цифр, но на смазанных, повернутых или плохо освещенных фото детекция баркода может не сработать (тогда используется fallback на полное фото).
- Фото скана сейчас сохраняется как data URL, что подходит для локального MVP, но не для production-хранилища.
- Текущая Prisma-модель все еще содержит техническую таблицу `Product`; ее смысл - хранить отсканированные артикулы, а не товарный каталог.

## Фаза 2 - Warehouse picking MVP

Статус: основа реализована.

Цель: склад получает удобный список товаров для пополнения.

Критерии успеха:

- Есть `Warehouse mode`.
- Товары сгруппированы по `storageSection` из этикетки.
- Storage-группы отсортированы по числовому `storageSection`.
- Внутри storage-группы сортировка: `article`, `season`, `color`.
- Запись товара компактная (1-2 строки):
  - строка 1: `article` и `needed sizes` плитками (акцентные, без `xN`);
  - строка 2: `color` с образцом выбранного цвета, `season`, справочно `present sizes` плитками (контурные).
- storage section показан как заголовок группы `Department {storageSection}`, а не в каждой строке.
- Товар можно отметить как `Taken` (взяли) или `Absent` (нет); статус сохраняется в `pickStatus` и восстанавливается.
- Техническое название сканированного артикула не показывается (совпадает с `article`).
- Клик по `article` открывает фото скана, если оно есть.
- Отсутствие фото обрабатывается текстовым сообщением.

Статус: не начато.

Цель: запустить приложение как Telegram miniapp, а не только как локальный мобильный веб.

Критерии успеха:

- Приложение доступно по публичному HTTPS URL.

Решения, которые нужно принять:

- Где хостить приложение.
- Как хранить фото сканов.
- Нужна ли авторизация через Telegram init data.
- Нужно ли хранить историю заявок между сменами.
