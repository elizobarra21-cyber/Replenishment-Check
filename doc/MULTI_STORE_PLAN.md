# Филиалы и права

Статус: код готов в ветке `multi-store` и проверен на локальной базе. На прод не выкачен: сначала нужна миграция базы (см. "Выкатка").

## Решения пользователя (2026-11-09)

1. Сотрудник может работать в разных филиалах, но у него есть филиал по умолчанию.
2. Личных настроек раскладки нет: правила меняют только администраторы, и сразу для всего филиала.
3. Новые сотрудники приходят по ссылке-приглашению. Существующие выбирают филиал по умолчанию из списка. Филиал легко сменить, например на время смены в другом магазине.
4. Администратор филиала видит сессии всех сотрудников этого филиала: только просмотр и PDF.
5. Больше между филиалами ничего не отличается. Отправка отчета на почту убрана, остается только необязательное сохранение PDF.

## Роли

| Роль | Область | Что может |
| --- | --- | --- |
| Администратор сети (`User.isNetworkAdmin`) | вся сеть | создавать и переименовывать филиалы, все права администратора в любом филиале |
| Администратор филиала (`StoreMember.role = ADMIN`), их может быть несколько | свой филиал | менять правила раскладки, приглашать и удалять людей, назначать администраторов, смотреть сессии филиала |
| Сотрудник | свои данные | работать со своими сессиями |

## Модель данных

Все изменения аддитивные. `User.layout` больше не читается, колонка оставлена, чтобы не удалять данные.

- `Store`: `name`, `inviteCode`, `layout` (форма `SizeLayout`, `null` = встроенные дефолты), кто и когда менял правила.
- `StoreMember`: пользователь, филиал, роль.
- `User`: `isNetworkAdmin`, `canPickStore`, `defaultStoreId`, `activeStoreId`.
- `ReplenishmentRequest.storeId`: сессия навсегда принадлежит своему филиалу.
- `RequestItem.targetTotal`: цель Y на момент добавления товара, чтобы смена правил не переписывала историю. У старых товаров `null`, для них Y считается как раньше.

## Как это работает

- Раскладка: встроенные дефолты -> правила филиала. Сервер берет правила филиала той сессии, к которой относится товар.
- Текущий филиал (`activeStoreId`) определяет правила на экране, список `Your sessions` и филиал новых сессий. Сессия из другого филиала остается там черновиком.
- Филиал по умолчанию меняется в Settings. Смена на время - кнопка `Change` рядом с названием филиала на главном экране; пока текущий филиал не совпадает с филиалом по умолчанию, рядом с названием написано `shift`.
- Первый выбранный филиал забирает все более ранние сессии пользователя.
- Пока ни одного филиала нет, приложение работает как раньше, на встроенных дефолтах и без экрана выбора.

## Вход в филиал

- Ссылка `/join/<code>`: код запоминается, пользователь проходит обычный вход, главный экран присоединяет его к филиалу.
- `User.canPickStore` разрешает выбирать филиал из списка. Его получают все существующие аккаунты (при выкатке) и те, кто пришел по ссылке. Новый аккаунт без ссылки видит экран "откройте ссылку от администратора".
- Администратор может выпустить новую ссылку, старая перестает работать.
- Удаление из последнего филиала снимает `canPickStore`: чтобы вернуться, снова нужна ссылка. Удаление из одного филиала при наличии других доступ к списку не отнимает: кто может выбирать филиал, тот может зайти в любой.

## Права

Проверяются только на сервере, в `lib/stores.ts`: `requestAccess` (владелец читает и пишет, администраторы филиала только читают, остальным 404) и `canManageStore`. Все маршруты заявок, товаров, склада, отчета и скана проходят через эти проверки.

Филиал нельзя оставить без администратора: последнего администратора нельзя снять или удалить (`409`), сначала нужно назначить другого. Правило действует и для администратора сети. Филиал, в котором администратора еще не назначали, работает как обычно.

## Экраны

- Главный: название филиала и `Change`, экран первого выбора, экран "нужна ссылка".
- `Settings`: филиал по умолчанию, ссылки на управление.
- `/settings/stores/[id]`: правила, ссылка-приглашение, люди и роли, сессии филиала.
- `/settings/stores/[id]/layout`: редактор правил филиала.
- `/settings/stores`: все филиалы и создание нового (администратор сети).

## Выкатка

Порядок важен: код из этой ветки обращается к новым колонкам, поэтому сначала база, потом код. `main` деплоится на Vercel автоматически при пуше.

1. `prisma db push` на прод (только добавление таблиц и колонок; перед этим проверить `prisma migrate diff`, что нет удалений).
2. Выполнить `prisma/multi-store-rollout.sql`, подставив email администратора сети.
3. Влить `multi-store` в `main` и запушить.
4. Администратор сети создает филиалы в `Settings -> All stores`. С этого момента сотрудники при входе выбирают филиал.
