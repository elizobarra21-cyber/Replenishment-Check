# План: филиалы, права и раскладка филиала

Статус: проект от 2026-11-05, кода нет. Реализация начнется после ответов на открытые вопросы в конце.

## Задача

Приложение нужно масштабировать на другие магазины сети. В каждом магазине свои правила раскладки (кто-то кладет по 4 вещи, кто-то по 5). Правила филиала меняет администратор, и сразу для всех сотрудников; администраторов может быть несколько. Обычный пользователь тоже может менять правила, но только для себя.

## Роли

| Роль | Область | Что может |
| --- | --- | --- |
| Администратор сети | вся сеть | создавать филиалы, назначать и снимать администраторов филиалов, видеть все филиалы |
| Администратор филиала | свой филиал (их может быть несколько) | менять раскладку филиала, управлять сотрудниками, видеть сессии филиала |
| Сотрудник | свои данные | работать со своими сессиями, менять личную раскладку только для себя |

Роль привязана к филиалу, а не к человеку: один человек может быть администратором в одном филиале и сотрудником в другом.

## Модель данных

Все изменения аддитивные, существующие данные не меняются.

```prisma
model Store {
  id              String   @id @default(cuid())
  name            String
  inviteCode      String   @unique
  layout          Json?    // раскладка филиала, форма SizeLayout; null = встроенные дефолты
  layoutUpdatedAt DateTime?
  layoutUpdatedBy String?  // кто последним менял правила
  reportEmail     String?  // сейчас адрес отчетов один на всех (REPORT_TO)
}

enum StoreRole { MEMBER ADMIN }

model StoreMember {
  userId  String
  storeId String
  role    StoreRole @default(MEMBER)
  layout  Json?     // личные отличия от раскладки филиала

  @@id([userId, storeId])
}
```

Также:

- `User.isNetworkAdmin Boolean @default(false)`.
- `User.activeStoreId String?` - текущий филиал, если их у человека несколько.
- `ReplenishmentRequest.storeId String?` - сессия принадлежит филиалу навсегда, даже если сотрудник перешел в другой.
- `RequestItem.targetTotal Int?` - см. "Снимок цели".

## Как считается раскладка

```text
встроенные дефолты -> раскладка филиала -> личная раскладка
```

Каждый уровень переопределяет отдельно сетку или список фронтов, все остальное наследуется. На практике:

- администратор меняет сетку филиала, и она сразу действует у всех, кто эту сетку лично не менял;
- у сотрудника с личной настройкой этой сетки остается его вариант; редактор показывает пометку "личная, отличается от филиала" и кнопку "вернуть правила филиала";
- расчетные функции уже принимают один `layout`, поэтому объединение делается в одном месте (`lib/user-layout.ts`) и остальной код почти не меняется.

В раскладку филиала стоит добавить и приоритет размеров: сейчас он общий на всю сеть (`SizeConfig.priority`).

## Снимок цели

Сейчас цель Y в `X/Y` считается заново при показе. Если администратор изменит правила, то старые сессии и PDF задним числом покажут другие цифры. Поэтому при добавлении товара цель нужно сохранять в `RequestItem.targetTotal`, а для старых товаров оставить текущий расчет. С правилами на весь филиал эта проблема станет заметной, поэтому снимок входит в первый этап.

## Вступление в филиал

Рекомендация - код приглашения: администратор показывает ссылку `/join/<code>` или код, сотрудник входит через Google и попадает в филиал с ролью `MEMBER`. Пользователь без филиала видит только экран ввода кода. Администратор может перевыпустить код и удалить сотрудника.

## Проверка прав

Права проверяются только на сервере, скрытие кнопок защитой не считается. Общие проверки в новом `lib/permissions.ts`: `requireStoreMember`, `requireStoreAdmin`, `requireNetworkAdmin`, `canAccessRequest`.

**Сейчас изоляции данных нет, и это нужно закрыть первым.** Проверка владельца есть только в `GET`/`PATCH /api/requests/[id]` и `/api/scan/history`. В `/api/requests/[id]/warehouse` нет даже проверки входа; `report`, `items/[id]` и `POST /api/scan` проверяют вход, но не владельца. Пока магазин один, риск невелик, но с несколькими филиалами так запускать нельзя.

## Интерфейс

- `Settings -> Store rules` - виден только администратору филиала. Тот же редактор, что `Customize layout`, с подтверждением "изменится для всех сотрудников филиала, N человек".
- `Settings -> Store members` - сотрудники, роли, код приглашения.
- `Settings -> Customize layout` остается личным и показывает отличия от филиала.
- `/admin` - для администратора сети: филиалы и их администраторы.

## Миграция

1. `prisma db push` с новыми таблицами и колонками (только добавление).
2. Создать первый филиал, всех текущих пользователей сделать его участниками, их `User.layout` скопировать в `StoreMember.layout`, старым сессиям проставить `storeId`.
3. Назначить администратора сети и администраторов первого филиала.
4. Раскладка первого филиала = `null` (дефолты), поэтому у текущих пользователей ничего не меняется.

## Этапы

1. Закрыть API проверками владельца и ввести `lib/permissions.ts`.
2. Схема, миграция, снимок цели.
3. Объединение раскладки в три уровня; редактор `Store rules`.
4. Приглашения и управление сотрудниками.
5. `/admin`, адрес отчетов по филиалам, просмотр сессий филиала.

## Открытые вопросы

1. Может ли сотрудник работать в нескольких филиалах? Предположение: да, модель это позволяет, в интерфейсе появляется переключатель.
2. Может ли администратор запретить личные отличия от правил филиала? Предположение: нет, по исходной просьбе личная настройка есть у всех.
3. Как сотрудник попадает в филиал? Предположение: код приглашения, без ручного подтверждения.
4. Видит ли администратор филиала сессии всех сотрудников? Предположение: да, только просмотр и PDF, без редактирования.
5. Что еще отличается между магазинами, кроме сеток и фронтов? Например, департаменты, порядок обхода склада, адрес отчетов. Сейчас департаменты общие: мужской отдел - `45**`, женский - `23**`.
